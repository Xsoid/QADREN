# Модель резервирования

Статус: **принцип принят**, форматы схем ещё проектируются.

## BackupSet

Логический набор данных с независимой конфигурацией. Предлагаемые поля (не окончательный формат): `id`, `endpoints`, `paths`, `mode`, `schedule`, `version_policy`, `deletion_policy`, `conflict_policy`, `verification_policy`, `transfer_policy`.

## Направления

1. **Яндекс → iCloud**: Яндекс — основной источник, iCloud — резерв.
2. **iCloud → Яндекс**: iCloud — основной источник, Яндекс — резерв.
3. **Яндекс ↔ iCloud**: обе стороны могут производить новые изменения; резервная история хранится отдельно от текущего состояния.

Правила применяются **к отдельным папкам/наборам**, а не ко всей учётной записи. В перспективе направлений/узлов больше двух.

## Версии

Каждое изменение формирует отдельную идентифицируемую версию. Не считать совпадение имени файла достаточным доказательством идентичности. Для двустороннего обмена нужна фиксация происхождения изменения и причинной истории, чтобы отличать конфликт от уже перенесённой версии.

## Конфликты

Одновременные независимые изменения **не разрешать по времени изменения автоматически**. Сохранять обе версии и передавать решение пользователю. Автоматическое слияние содержания документов вне начального объёма.

## Удаления

Удаление в рабочей папке — логическое событие (tombstone), а не команда удалить все версии повсюду. Физическое удаление старых резервных версий — отдельная политика удержания и подтверждений. Массовые удаления должны вызывать защитную остановку или подтверждение; конкретные пороги ещё не определены.

## Статусы (предлагаемый словарь)

`DISCOVERED`, `QUEUED`, `AWAITING_APPROVAL`, `TRANSFERRING`, `VERIFYING`, `PROTECTED`, `FAILED`, `UNKNOWN`.

Имена и переходы состояний до реализации требуется формализовать.
