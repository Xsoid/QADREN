# Архитектурный обзор

Статус: приняты принципы продукта v0.2; релиз 1 — локальная версия, удалённые Worker — после неё.

## Назначение

QADREN — система синхронизации и обмена файлами между локальными, облачными и удалёнными хранилищами с автономным исполнением заданий. Не является обязательным локальным зеркалом облаков.

## Логические части

- **Core**: сценарии, задания, контрольные метаданные синхронизации, состояния, планирование и журнал.
- **Controller**: настройка правил, назначение задач, получение результатов и мониторинг.
- **Worker**: непосредственное выполнение назначенных операций.
- **Storage Adapter**: совместимость и операции конкретного хранилища.
- **Scenario**: независимая конфигурация синхронизации; **Job**: конкретное выполнение или разовая файловая операция. BackupSet отложен (см. backup-model.md).
- **Execution Report**: сообщение Worker о выполнении, ошибках и доказательствах.
- **Local Download Policy**: правило загрузки содержимого на конкретном узле.

Эти роли логические. Один экземпляр приложения может совмещать Controller и Worker, но делегирование не даёт контроллеру права скрыто выполнять чужую задачу.

## Платформенность

Архитектура **кроссплатформенная**. Конкретные возможности определяются ОС, правами пользователя и адаптером. iCloud Documents привязан к поддерживаемой Apple платформенной интеграции. Не создавать глобальное ограничение macOS для остальных интеграций.

## Ограничения

- Контроллер не обязан видеть или скачивать содержимое файлов.
- Нельзя считать успех локальной записи в iCloud доказательством того, что копия уже надёжно хранится в облаке.
- Отдельное устройство может исполнять задания автономно по ранее полученным правилам.
- Протокол связи, обнаружение узлов, распределённые блокировки и переизбрание контроллера **отложены**.
- Стек **Rust Core + SwiftUI macOS + Swift iCloud adapter + SQLite** принят; точные схемы, ABI и процессы уточняются. См. [стек](technology-stack.md).

## Актуальная спецификация

[QADREN v0.2](backup-model.md) — источник продуктовых требований. Собственные архивы версий файлов и обязательный BackupSet не входят в MVP.

## Принцип компактности

Минимальная фоновая активность, никаких постоянных полных зеркал на главном MacBook, никакого обязательного тяжёлого серверного стека. Конкретные ресурсы и размеры установить по итогам измерений.


## Фактическая архитектурная база (аудит 2026-10-11)

В `main` существуют: Rust модели `model.rs`, capabilities `capabilities.rs`, `JobStore` + attempts/events/expectations в `jobs.rs`, `confirmation.rs` и `verification.rs`, `Registry` в `registry.rs`, Yandex metadata/OAuth/Keychain и начальный streaming upload, защищённый частичный Local FS, narrow Registry/Yandex FFI и SwiftUI экран подключений. Нет доказанной сквозной Job → адаптер → durable verification → SwiftUI операции; сценарное исполнение, scheduler, iCloud Documents container и независимая служба не завершены. Реализованная SQLite JobStore — основа, не переписывать вторую очередь.

### Владение и зависимости

- **Controller** (локальная логическая роль): редактирует Scenario, задаёт расписания, формирует Job, показывает отчёты; не выполняет порученное другому Worker задание.
- **Worker / Rust Job execution:** единственный исполняющий компонент каждого attempt; в первом инкременте хостится внутри SwiftUI процесса без привязки бизнес-логики к Swift; позже тот же engine перемещается в службу. Ownership и durable attempt фиксируются до внешнего эффекта.
- **Storage Adapters:** независимые экземпляры по `connection_id`; платформенные prerequisites и правдивые capabilities, метаданные без скрытого чтения контента, streaming, evidence и детерминированная классификация ошибки/неопределённости; не принимают решения UI.
- **Policy:** предварительный authorization/consent, оценка конфликта/массовых удалений и пост-проверка перед изменяющим I/O; предварительный stat не является атомарной гарантией при конкурентных мутациях.
- **Scenario:** план diff относительно последнего подтверждённого `FileSyncState`, ревизии и directional rules; не выполняет I/O напрямую.
- **SQLite:** источник истины для connections, Jobs/attempts/events, FileSyncState, решений и служебной истории. Registry и JobStore существуют отдельно; объединение файлов/транзакций не делать без доказанного требования. При disconnect запретить новые Jobs и согласовать уже активные attempts до удаления Keychain reference.
- **FFI:** версионируемые команды/результаты и ownership памяти; не экспортировать произвольные внутренние структуры Rust или секреты. SwiftUI отображает durable state, направляет команды и подтверждения.

### Инварианты интеграционного исполнения

1. Валидация scope, подключения, platform/capability и consent; неподтверждённые права дают отказ без I/O.
2. Стабильный `job_id`/`attempt_id` и целевой путь/операция сохраняются в SQLite **до** внешнего эффекта.
3. Изменяющий I/O допускает проверку актуальности непосредственно перед эффектом; no-overwrite для первой вертикали.
4. Ответ adapter — не обязательно доказательство целостности. Verification возвращает уровни evidence; completion только при достаточном уровне и соответствующем attempt.
5. Сбой после возможного внешнего эффекта → `UNKNOWN`, затем read-only reconciliation. Blind retry запрещён, включая timeout и crash.
6. Отмена/пауза после возможного эффекта не стирает attempt; сохраняется частичный прогресс и необходимость сверки.
7. Коммит Job result и события в SQLite выполняется согласованно; UI перечитывает фактическое durable состояние.
8. Ограничения платформ фиксируются в capabilities по факту реализации. `AdapterCapabilities` из `lib.rs` и `CapabilityDeclaration` из `capabilities.rs` нужно согласовать без изменения ABI вслепую.

### Явные решения до Release 1

Старт исполнения внутри SwiftUI, но Rust владеет engine и SQLite. Destructive Local FS fail-closed до доказательства безопасности конкурирующих изменений; решение о выпуске с ограничениями принимается отдельно. App Store против прямой signed/notarized поставки пока открыто; сначала native spike iCloud entitlements + service lifecycle.
