### Стабильность задач и источников требований

**Нумерация issues стабильна.** Изменение приоритета `P0/P1/P2/P3` — это **редактирование существующей задачи**, а не её замена, переиздание или изменение номера. Не использовать диапазоны вида `P1–P2` для дочерних issues: у каждой один текущий стартовый приоритет; последующие критерии приёмки остаются в этой же issue. Epic #12 может охватывать все этапы. **Единственная новая тематическая P0 issue после аудита — #26** для уже существующего UI; исходная #13 архивирована `not planned / superseded`, её незавершённые требования зафиксированы в #26/#24/#25. Не плодить новые «аудит», «стабилизация» и «новый план» issues.

**Иерархия:** продуктовые решения и safety policies → D-018 (приоритеты) → этот исполнимый roadmap (распределение) → профильная архитектура и дизайн (как должно работать) → конкретная issue (объём работ) → фактический код и проверенные тесты (стадия готовности). **Исторические формулировки ниже блока D-018 в issues не создают повторного обязательного scope.** При изменении последовательности править существующие документы и issues без создания параллельных спецификаций. Нормативные гарантии безопасности и подтверждённые функции нельзя удалять из требований ради перестановки очереди.

Предыдущая детальная дорожная карта и G0–G6 сохранены в [истории Git на `44538fe`](https://github.com/Xsoid/QADREN/blob/44538fe480ab17e3ee0c6114aaa3762a1c35d8c9/docs/roadmap.md) как архивный план, а не вторая актуальная спецификация.

**Для P0:** #26 — единственная активная P0 issue; #13 архивная, её незакрытые проверки распределены по #26/#24/#25. Не ждать выполнения G1/G2/Yandex, не изобретать runtime-данные. **Для P1:** G1 app-owned mock уже существует в `job_execution.rs`; не переписывать его как отсутствующий. Следующий критерий — **реальная локальная, безопасная, привязанная к Job операция**, а не новый mock. В P2 не смешивать readiness фоновой службы с готовностью интерфейсных компонентов.

**Локальные release gates:** успешная сборка и тесты на зафиксированном SHA; UI без mock-метрик; сценарий Local↔Local с recovery/consent; работающая независимая служба и установка. **Cloud gate отдельный:** провайдер доступен, контракт актуален, live E2E и safety proven. P0–P2 не блокируются P3. Политики из `docs/policies/` остаются обязательными.

### Приёмочные сценарии локального релиза P0–P2

- Для локальных подключений сохраняются независимые connection_id; облачная независимость credentials остаётся инвариантом к будущему P3 и не блокирует локальный выпуск.
- One-way и two-way обнаруживают изменения по последнему согласованному состоянию и сигнализируют об неоднозначных конфликтах; одинаковое имя/размер не доказывают равенство байтов.
- События, поступившие во время Job, создают один следующий Job; состояние старого Job и его ревизия не переписываются.
- Повторный запуск, сбой питания и повторный старт не запускают опасную операцию дважды без проверки её результата.
- Ручное задание получает начальный приоритет, автоматическое не голодает бесконечно; локальная пауза сохраняется после reboot.
- Запрос предпросмотра не передаёт содержимое на основной MacBook; загрузки содержимого требуют явного индивидуального согласия.
- Массовое удаление и неразрешённый конфликт не приводят к молчаливому уничтожению данных.
- В дереве Job работают multiselect и операции над вложенными файлами без двойного счёта; прогресс показан в байтах и файлах.
- Закрытие UI не прерывает службу; повторное открытие восстанавливает окна/панели/навигацию и перечитывает актуальные состояния.
- Неизвестная квота/ETA/состояние Worker не отображается как проверенный успех.
- Яндекс Диск и iCloud не являются условиями локального релиза; новые Yandex-подключения в P0–P2 помечены отложенными, прежние подключения/секреты сохранены. Ни одна неподтверждённая облачная операция не выдаётся за доступную.

## Релиз 2 — удалённые Worker

- Разработать и отдельно утвердить транспорт, взаимное доверие, доставку команд, подтверждения, ревизии, журнал и идемпотентность.
- Worker обслуживает локальные разрешения/авторизацию и оперативные задания; сценарии изменяет Controller.
- Controller назначает сценарий вручную совместимому Worker; дистанционная недоступность не означает остановку.
- Переназначение требует подтверждения release прежнего Worker; принудительный disconnect оставляет UNKNOWN Jobs заблокированными до сверки.
- При повторном pairing выполняется сопоставление состояний; UI Worker остаётся локальным.
- Проверить выполнение при отключённом Controller и последующую загрузку отчётов без повтора эффектов.

## Отложено

**iCloud Documents, синхронизация и бекап с iCloud:** будущая возможность, не Release 1. Не разрабатывать контейнер/adapter, UI, entitlements/native spike или iCloud E2E; исходная #17 закрыта как not planned. Возобновить только по отдельному продуктовому решению после проверки бесплатного/платного способа доступа, платформенных требований и облачного подтверждения. См. [D-017](decisions/D-017-defer-icloud.md).

BackupSet, резервные версии и восстановление старого содержимого; межсценарные зависимости; пользовательские ACL Worker; собственный поисковый индекс; аналитика изменения квот; удалённый UI Controller; обновление ПО Worker из Controller.

## Негативные проверки

Нельзя тестировать сохранность только happy-path. Нужны обрывы связи, API 429/5xx, истечение токенов, частичная запись, повторные уведомления, смена времени/DST, недоступность назначения, race между delete/reconnect и локальной паузой. Результаты тестов фиксировать отдельно от планов.
