# Правила разработки QADREN

Статус: **обязательные правила для новых патчей**. Читайте также [AGENTS.md](../../AGENTS.md).

## 1. Минимализм

- Начинать с самого простого решения, покрывающего текущий сценарий.
- Не создавать абстракции для воображаемых интеграций. Расширяемость через узкий проверяемый контракт адаптера.
- Не добавлять отдельный daemon/process, HTTP-сервер, IPC или scheduler без доказанной необходимости.
- Не дублировать бизнес-логику Rust в Swift UI. UI отображает состояние и отправляет намерения.
- Разделять логические модули; **не создавать отдельный crate для каждой сущности**.
- Каждая внешняя зависимость: зачем нужна, альтернатива, влияние на бинарный размер, поддержку и безопасность.

## 2. Границы модулей

- Общая логика резервирования, состояние и правила — Rust, без импорта Apple API.
- Платформенные возможности — отдельные адаптеры/обвязка.
- Rust/Swift взаимодействие через ограниченный FFI: явное владение памятью, обработка ошибок, безопасная отмена задач.
- Типы и ошибки адаптеров должны описывать **поддерживаемость операции**, а не просто success/failure.
- Не выдавать принятый Яндекс API upload за полностью подтверждённую облачную копию. iCloud transfer/adapter отложены по D-017; не внедрять их в текущие функциональные Issues.
- Отложенные сетевой протокол и межузловую синхронизацию не реализовывать «на всякий случай».

## 3. Сохранность и приватность

- Никаких destructive операций без явно предусмотренной политики, проверенной защиты от конкурентных изменений и достаточных подтверждений. Собственного версионирования файлов в текущем релизе нет; до доказанной безопасности операция остаётся fail-closed.
- Нет «last writer wins» для независимо изменённых файлов.
- Выполнение делегированного задания принадлежит только Worker. Controller не перепроверяет содержимое скачиванием.
- Любой путь к скачиванию **по инициативе QADREN** на основной MacBook проходит через механизм разрешения. Не мешать macOS/iCloud и другим программам.
- OAuth-токены и ключи не должны попадать в исходники, логи, тестовые фикстуры или Git.
- Логи по умолчанию не записывают содержимое файлов, токены или приватные URL с авторизацией.

## 4. Ошибки и сбои

- Ошибки должны быть типизированными и контекстными.
- Любое задание переживает перезапуск или переводится в явное восстанавливаемое состояние.
- Повтор операции идемпотентен либо запрещён до выяснения удалённого результата.
- Не превращать timeout в «задача точно не выполнена».
- Не подавлять ошибки и не отмечать отсутствие проверки как успех.

## 5. Изменение проекта

- Один связный функциональный пакет — одна цель, её тесты и review. Работать непосредственно в `main`; PR и дополнительные ветки не обязательны.
- Перед изменением читать README, профильную спецификацию, журнал решений и тесты.
- Если патч меняет принятый принцип — сперва предложить изменение ADR, явно указать несовместимости.
- В том же функциональном пакете обновлять документацию и тесты; новые решения не оставлять исключительно в чате или issue.
- Не заявлять об успешной проверке без фактического запуска команды.


## Codex workflow для Release 1 (2026-10-11)

- **Start:** прочитать AGENTS.md, актуальные #12 и свою Issue, docs/roadmap.md и конкретные файлы кода; назвать уже существующие API и baseline SHA. Никаких вторых JobStore/Policy/Registry или веток для документации.
- **Plan:** задать функциональную вертикаль, контракты на Rust/Swift/SQLite/FFI boundary, внешние эффекты, scope consent, UNKNOWN reconciliation и критерии завершения. Если платформенное ограничение не доказано — feature fail-closed.
- **Implement:** один целостный пакет с behaviour test + negative/fault matrix, а не серия косметических фиксирующих тестов без функции. Первый runner хостится SwiftUI in-process, Rust engine остаётся независимым от UI и пригодным для service extraction.
- **Verify:** `bash scripts/test-core.sh`, применимые macOS Swift/FFI scripts, mock HTTP и реальные platform tests там, где они необходимы. Не путать mock PASS с реальной безопасностью macOS/облака.
- **Review:** code review correctness, ownership и ABI; security review content policy, paths, races, secrets, overwrite, cancellation, reconciliation. Explicit diff review, затем коммит непосредственно main. Не объявлять Done без приемочных доказательств.
- **Report:** commit SHA, проверенные и непроверенные критерии, версию среды, известные риски. После законченного пакета обновить Issue и документацию. GitHub Actions необязательны. Не переключаться в Work автоматически.


## Интеграция AI-Docs-Hub: порядок для чата и Codex

Это дополнение к обязательной политике совместимости в `AGENTS.md`. AI-Docs-Hub — опциональный dev-tool, не часть QADREN runtime.

1. **Onboard без записи:** запустить `python3.11 scripts/onboard-project --project <qadren-project-id>` из установленного AI-Docs-Hub (подставить фактический ID после создания project config). Аналогично `scripts/scaffold-project-docs --project <id>` без `--write`. Просмотреть действия и diff; не принимать генерацию параллельных архитектурных каталогов.
2. **Write только осознанно:** убедиться, что Hub добавляет максимум idempotent managed block в существующий root `AGENTS.md`; при непустых документах QADREN write запрещён, если меняет их смысл или размещение. Уточнить конфигурацию включений/исключений, исключить credentials, временные transfer файлы, SQLite и локальные артефакты.
3. **Контекст:** агент начинает с QADREN `AGENTS.md` и действующих `docs/`, использует Hub RAG/Codebase Memory только как навигационный индекс с проверкой свежести относительно HEAD. Chat без Hub делает ровно те же шаги напрямую по репозиторию.
4. **Проверка изменений:** canonical команды QADREN (`bash scripts/test-core.sh`, `bash scripts/build-macos.sh` на macOS плюс профильные тесты) остаются главными. Hub verify/review добавляет evidence, но не заменяет native или живой provider E2E. До публикации обязательны code review и security review независимо от доступности Hub.
5. **Результат:** обновить соответствующую GitHub Issue с SHA, environment, PASS/FAIL/SKIPPED/BLOCKED, mock-vs-real evidence и известными рисками. Никогда не записывать в Hub secrets, пользовательские файлы или содержимое transfer; избегать git-tracked Hub-generated snapshots внутри QADREN.

Установка Hub на машине и создание локального project binding — отдельное действие, **не** выполняемое автоматически изменениями этого документа. Директивы QADREN имеют приоритет над типовым шаблоном Hub.


## Автономная передача между сеансами (Chat → Codex → Chat)

**Назначение:** агент может смениться в любой момент; память чата и индекс AI-Docs-Hub не считаются источником истины. Продолжение работы определяется только текущим `main`, актуальной GitHub Issue и документацией. Не создавать параллельный state-файл или вторую доску задач.

### Начало сеанса

1. Проверить `git status -sb`, `git rev-parse HEAD`, `git pull --ff-only origin main` **только при чистом дереве**; при чужих незакоммиченных изменениях не перезаписывать их и не выполнять force/reset. Сверить текущую Issue и её комментарии, учесть коммиты после последней записи.
2. Прочитать `AGENTS.md`, `docs/roadmap.md`, профильные политики/ADR, `docs/development/release-1-validation.md`. При подключённом AI-Docs-Hub проверить context freshness относительно HEAD; при отсутствии Hub читать репозиторий напрямую.
3. Выполнить **existing-code inventory**: найти реальные публичные API, миграции, тесты и уже реализованные части; не доверять старым номерам строк и старым SHA в Issue. В частности, #18 уже имеет `JobStore::list_jobs`, `jobs_ffi.rs` и Swift `JobInventory`; это **read-only**, не исполнение.
4. Выбрать **одну готовую по зависимостям** Issue из Epic #12. Если в текущей Issue нет свободного функционального scope — перейти к следующей готовой, не писать новый продуктовый код только ради активности.

### Перед коммитом

- Указать целевое пользовательское поведение, вход/выход, границу изменений, какие существующие API переиспользуются, какие риски fail-closed, отрицательные сценарии.
- Не выполнять destructive операции на пользовательских данных, live transfer или скачивание содержимого на основной MacBook без нужного согласия; для безопасных unit/mock fixtures отдельное продуктовое разрешение не требуется.
- Проверить скрипты и сохранить отчёт по каждому из: `PASS`, `FAIL`, `BLOCKED` (отсутствует среда/секрет/разрешение), `SKIPPED` (не относится). `NOT RUN` не означает `PASS`.
- Провести самостоятельный code review и security review. Если нет механизма независимой проверки, явно отметить ограничение. Не обходить запреты посредством отключения lint или подделки подтверждений.

### Завершение сеанса / передача

В комментарии к рабочей Issue (либо в отчёте пользователю, если запись GitHub недоступна) оставить компактный handoff: `HEAD/base SHA`, коммиты, подтверждённо готовое поведение, точные команды и результаты, непроверенные свойства и риски, следующий **конкретный** acceptance step, блокеры, решения владельца. Нельзя выдавать изменение read-only UI за завершённый Job Engine. Если GitHub-комментарий недоступен, не создавать ради этого новый документ с журналом сессий.

### Когда нужен владелец проекта

Запрашивать решение только при изменении продуктовых инвариантов/архитектуры, неизбежном риске потери данных, выборе distribution, разрешении выпуска без обязательных возможностей, реальной авторизации/секретах или доступе к машине, недоступной агенту. Обычные проектные решения, безопасный mock, рефакторинг по правилам и подготовка Issues не требуют отдельного согласования. Если блокер касается одного потока, продолжить независимый поток по `docs/roadmap.md`.

**Политика Hub:** onboarding и scaffold только после dry-run и diff; сохранение существующих документов. Hub checks являются дополнительными источниками evidence, но не заменяют native tests и опубликованный `main`.

## Политика вычислительной экономии для Plus

- Базовая рекомендованная модель Codex: **GPT-5.6 Terra**, умеренное reasoning; при выборе модельного режима на стороне пользователя соблюсти этот default. Модель не является частью runtime-архитектуры QADREN.
- Разбивать работу по функциональным Issue и конкретным acceptance, ограничивать объём контекста нужными исходниками; не перечитывать весь репозиторий и не запускать полный глубокий архитектурный анализ на каждом патче.
- Тратить повышенное reasoning только на узкие вопросы безопасности, SQLite recovery, параллелизма, FFI ownership и потенциальной потери данных; повышение до GPT-6 Astra/другого дорогого режима требует отдельного согласования владельца, а не автоматической эскалации.
- Не сокращать обязательные тесты, code/security review или fail-closed проверки ради экономии токенов. Вместо этого переиспользовать результаты проверок с тем же SHA, когда они действительно применимы.
- Конфигурация модели и фактическое использование лимитов управляются интерфейсом/настройками Codex, а не `AGENTS.md`. Агент выполняет политику best-effort и не утверждает, что переключил модель без реальной возможности это сделать.
